## Project Writeup : Summer Orienteering

Based on the path file, points are reached sequential from conduction numerous A* search’s one after another, with one search’s target, becoming the next searches starting node. If 7 destinations need to be reach with number 1 being the start, and number 7 being that same position to return to and end on, then 6 total A* searches will take place. The total across the pixel nodes of the best found path for a singluar A* search is returned to performOrienteering method, calling upon each one of these A* searchs by looping through the destinations placed in a twoDimension array of two columns of x and y for all the coord values. A total path length global is summed along the way, and this final cost is presented at the terminal, once the path has been found, but is not drawn on the output image. A 2D array of rgb integer values, one for each pixel, to output a final image is passed into each A star search, and returned with updating integer values, as we loop out searches, we continually pass along the returned pixel array, being cumulatively updated with the proper rgb int color of red for every pixel that is a part of the path and is to be shown on the output img. At the end of the program the rgb int array is translated to the output image all at once.

For implementing A* specifically, a priority queue was used to represent the frontier. If two paths occur to a state, being that a node appears on the frontier more than once, so long as that node hasn’t already become a parent in the overall path, and is still only on the frontier, both instances of that node will be added to the priority queue, but we will only ever consider the first instance, and instance of best path because whenever we pop a node we mark it in a visited set represented by a 2D, array. When the second instance of that node on the frontier is popped off the queue, we notice that that node is already in the visited set and disregard that node. The visited set is simply a 2d array of 0s and 1s for true and false. Once finding the target node for a specific a A*, the method paintTraversedPath (changing the rgb int values for pixels as mentioned above) makes use of a hashmap, coordToParentPairDict, of Key String to Value Node. This Dictionary is used individually for each respective A star search, and for all generated nodes, on the path found or not, there is a string representation of that node, mapping to the actual node instance of its parent. When paintTraversedPath is called on finding a target in the A\*, we use the dictionary to find the target nodes parent, then find the parent’s parent, and so on, backtracking through our path found, identifying the coordinates that mark nodes on the path found and need to be have their integer rgb representation changed to red.

## Cost Function Implementation

The cost for a given node in question, being the cost to reach that node from a starting node, is determined by adding the parent node’s cost value, plus the cost to move from parent to the child successor node in question. We take the 3d distance: being a change in x, change in y (which will both always be 1) and a change in z(elevation) . The change in x is multiplied by 10.29 to account for real world pixel size, and similarly the change in y is multiplied by 7.55. We then square all three values, and then taking the root of the sum of the three squares. We then take the average of the terrain multiplier for the parent and the terrain multiplier for the successor in question, under the idea that traveling from parent to successor spends half time in each terrain. This average terrain is multiplied by the prior distance root the calculate the complete cost from moving from parent to that successor. As stated this value is added to the parents cost, to determine the final cost for the node in question. The methods used for this are, calculategOFn and calculateDistance. Validity stands in simply adding to the cost of the parent, because when implementing proper functionality of the a Star search, for any node being generated on the frontier, the path to reach that nodes parent is the best possible path to that parent, and there will never be a path of better cost.

## Heuristic Implementation

The heuristic implemented in the A\* search present in this lab does its best job to estimate the cost of the cheapest path from the current node in question to the goal state. The heuristic calculated for a specific node is calculated by multiplying the straight line distance from that node to the goal node, by the easiest terrain to cross, which is the pavedRoad in this case, with a terrain multiplier of 1.0. Multiplying the straight line distance by the best possible terrain available is a simple way to do the heuristic, because given we are unsure of the terrain that lies on the path ahead, and can only see the terrain of the next possible node, simplifying the the search to a best goal state by assuming all terrain is fixed to a default traverse difficulty is valid.

The straight line distance referred to is calculated in the same manor mentioned in calculating the cost for a node. We take the delta values: being a change in x, change in y and a change in z(elevation) ALL from a the node to the goal state. The change in x is multiplied by 10.29 to account for real world pixel size, and similarly the change in y is multiplied by 7.55. We then square all three values, and then taking the root of the sum of the three squares to get this straight line distance.
